# 02. 전용 메커니즘 분석 → 최적 운용법·규칙 도출 설계

작성일: 2026-10-13 · 선행 문서: `01-research.md`

## 0. 왜 필요한가

고유 키워드(전체 인격 중 2개 이하에서만 등장)를 가진 인격 비율:

| 시즌 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 비율 | 4/49 | 6/22 | 11/23 | 17/22 | 16/21 | 22/23 | 25/25 | 4/4 |

키워드 374종 중 299종이 희귀 키워드. **최신 인격의 성능은 전용 메커니즘 운용이 결정**한다.
→ 정적 점수 모델(01 문서)만으로는 부족하고, 메커니즘을 **실행 가능한 모델**로 바꿔야 "최적 사용법"을 도출할 수 있다.

## 1. 목표 산출물 정의

인격마다 다음을 **근거(계산/시뮬 결과)와 함께** 생성:

1. **자원 흐름도**: 전용 자원(예: 보존, 검은 신의 가호)의 생산원·소비처·감쇠·상한
2. **브레이크포인트**: 성능이 계단식으로 바뀌는 임계값 ("합 4당 +1 (최대 3)" → 12에서 포화)
3. **가동 타임라인**: 핵심 상태 도달까지 걸리는 턴 수 (최소/기대값)
4. **상태별 운용 규칙**: "보존 횟수 < 12면 X, ≥ 12면 Y", 스킬 우선순위, 사용 순서
5. **팀 요구사항**: 이 인격이 제대로 돌려면 필요한 아군 조건 (소속, 키워드 공급자, 충전 인격 수 …)
6. **함정**: 하면 손해인 행동 (자원 부족 시 못 부여 실패, 상한 초과 낭비 등)

## 2. 전체 구조

```
 원문 텍스트 + 키워드 사전(446)
        │  ① LLM 컴파일 (Claude Code 에이전트 루프: 작성 → 테스트 → 수정)
        ▼
 Mechanic Spec (인격별 플러그인)  ◀── ② 검증: 단위 테스트 / 역번역 diff / 사람 검수
        │
        ├──▶ ③ 정적 분석 (시뮬 없이)         → 자원 흐름도, 브레이크포인트, 가동 턴 수 하한
        │
        ▼
 ④ 전투 엔진 (공통 규칙 하드코딩 + 인격 플러그인)
        │
        ▼
 ⑤ 정책 탐색 (시나리오별: 단일 보스 / 다수 적 / 내성 프로필)
        │   greedy vs 탐색(MCTS/롤아웃) 비교, 로그 수집
        ▼
 ⑥ 규칙 추출 (결정 트리 + 민감도 분석 → LLM이 자연어 가이드로 요약)
        │
        ▼
 인격별 운용 가이드 (구조화 rules + 근거 수치)  ──▶ 팀 최적화 / Agent 답변의 근거
```

## 3. 각 단계 상세

### ① Mechanic Spec: DSL + 탈출구(코드) 하이브리드

전용 메커니즘은 공통 패턴의 조합이 대부분이다. 그래서:

- **상태 변수**: `resource(name, owner=self|target, cap, decay_per_turn, kind=count|potency)`
- **이벤트 훅**: `on_stage_enter, on_turn_start, on_combat_start, on_use, before_attack, on_coin_start, on_hit, on_clash_win, on_attack_end, on_turn_end, on_ally_attack, on_ally_hit …`
- **조건**: `cmp(state, op, value)`, `per(state, n, max)` (N당 +1, 최대 k)
- **행동**: `gain / apply / consume / convert / burst / replace_skill / extra_attack / buff_ally(selector)`
- **아군 선택자**: `ally(affiliation="르누아르", order_by="charge_count", asc, n=1, exclude_self)`

DSL로 안 되는 ~10%는 **엔진 API를 쓰는 Python 훅**으로 작성 (LLM이 작성, 테스트로 검증).
Claude Code로 인격 1개당 "원문 읽기 → spec 작성 → 테스트 생성 → 실행 → 수정" 루프를 돌리는 방식이 현실적.

### ② 검증 (가장 큰 리스크 = spec 오역)

- **원문 기반 단위 테스트**: LLM이 문장마다 시나리오 생성
  예) "보존 횟수 12, 약속된 못 부여 → 못 +1 추가, 보존 -4" / "보존 1 → 못 부여 안 됨"
- **역번역 diff**: spec → 자연어 재생성 → 원문과 의미 비교 (다른 모델/다른 샘플로)
- **다중 샘플 합의**: 같은 원문을 N번 컴파일해서 불일치 지점만 사람 검수 큐로
- **실측 대조**: 플레이어(사용자)가 실제 전투 수치를 기록 → 엔진 결과와 비교 (데미지 공식 보정용)

### ③ 정적 분석: 시뮬 없이 뽑을 수 있는 것부터

spec은 그래프이므로 바로 분석 가능:
- 자원별 **생산량/턴 vs 소비량/턴** (최대·기대) → 자립 가능? 아군 의존?
- `per(…, max)`, `cmp(≥ k)` 에서 **브레이크포인트 자동 추출**
- 상한 + 턴당 획득 제한 → **핵심 상태 도달 최소 턴 수**

#### 예시: #204 돈키호테 (르누아르 브랜드 매니저), 동기화 4 — 손 계산, 미검증

| 자원 | 생산 | 소비 / 감쇠 | 상한·제한 |
|---|---|---|---|
| 보존 횟수 | 첫 등장 +10, S1코인2 +6, S2코인2 +8, S3코인3 +4, 수비 전투시작 +4 · 코인2 +4 | 못 부여 시: ≥12면 -4(못+1), <12면 -2, 부족하면 못 부여 실패 / 턴 종료 -1 | 20 |
| 보존 위력 | 보존 누적 소모 10당 +1 | — | — |
| 검은 신의 가호 | 첫 등장 25, 보존 소모·초과량 ×5, 보호막 아군 피격 +2(충전 인격 +5) | 강화 S3 공격 종료 시 전부 소모 | 100 / 소모 경로 턴당 30, 피격 경로 턴당 10 |

여기서 기계적으로 나오는 규칙 후보:
- **가호 100 도달 최소 ≈ 2~3턴** (25 + 30/턴 + 피격 ≤10/턴) → 수비 스킬이 '거듭 내리쳐…'(가중치 3)로 바뀌는 사이클
- **보존 위력 3(스킬 코인위력+1·피해량 조건)** = 누적 소모 30 → 못 부여(≥12일 때 4 소모) 약 8회 필요 → 늦게 켜지는 조건, 초반 기대치에서 빼야 함
- **S2는 코인1(못 부여·소모)이 코인2(보존 +8)보다 먼저** → 보존 12 미만에서 S2를 쓰면 못이 덜 붙음 → 같은 턴에 보존 생산 스킬을 먼저 쓰는 순서가 유리할 수 있음
- **'심판!' 자동 공격은 다른 르누아르 아군이 공격해야 발동** → 팀 요구사항: 르누아르 소속 1명 이상 (#202 료슈, #203 로쟈 등) — 충전 공급 패시브도 르누아르/충전 인격 대상

이런 결론은 **시뮬 없이 spec만으로** 나온다. 1차 목표로 적합.

### ④ 전투 엔진

- **공통 규칙은 한 번만 하드코딩**: 속도/턴 순서, 코인 판정(앞면 확률 = 50% + 정신력%), 합, 피해 공식(내성·속성 배율), 흐트러짐, 정신력 변화, 표준 키워드(출혈/파열/진동/침잠/화상/호흡/충전 — 키워드 사전 정의 그대로), 스킬 덱(S1×3/S2×2/S3×1)과 손패.
- **목표 정확도는 "상대 정확도"**: 절대 데미지가 게임과 똑같을 필요는 없고, **선택지 간 우열이 맞으면 충분**. 공식이 불확실한 부분은 파라미터로 빼서 민감도 분석.
- **적은 시나리오 라이브러리로**: 허수아비(합 안 함), 단일 보스(고정 위력 합), 다수 잡몹, 내성 프로필 몇 종. 실제 적 패턴 재현은 후순위.

### ⑤ 정책 탐색

인격 운용의 의사결정 = 매 턴 **어느 스킬을, 어느 순서로, 누구에게, 합/일방, E.G.O 사용 여부**.
- 기준선: 랜덤, 탐욕(즉시 기대 피해 최대)
- 탐색: 짧은 롤아웃 / MCTS (턴당 선택지가 작아서 충분히 가능)
- **탐색이 탐욕과 다른 선택을 한 상태 = 운용 노하우가 존재하는 지점** → 이걸 집중 수집

### ⑥ 규칙 추출

- 로그 `(상태 특징, 최적 행동, 이득)` → **얕은 결정 트리**로 학습 → 분기 조건이 곧 규칙 ("보존 ≥ 12 그리고 가호 < 100 → S2 우선")
- **민감도 분석**: 자원 초기값/아군 구성 하나씩 바꿔가며 성능 변화 → "르누아르 아군 0명이면 -35%" 같은 팀 요구사항 정량화
- LLM은 **요약·설명만**: 트리와 수치를 받아 가이드 문장 작성. 근거 없는 주장 금지 (모든 문장에 근거 수치 링크).
- 커뮤니티 공략과 교차검증: 결론이 다르면 "spec 오류인지, 새 발견인지" 검수 큐로.

## 4. 산출 데이터 예시 (인격 운용 가이드 스키마)

```json
{
  "identity_id": 204, "uptie": 4, "spec_version": "a1b2c3", "engine_version": "0.1",
  "resources": [{"name": "보존", "cap": 20, "net_per_turn": {"min": -2, "expected": 5.1, "max": 14}}],
  "breakpoints": [{"var": "대상 진동 위력+약속된 못", "values": [4, 8, 12], "effect": "S1/S2 최종 위력 +1씩"}],
  "milestones": [{"state": "검은 신의 가호 = 100", "turn_min": 3, "turn_expected": 3.4}],
  "rules": [{"when": "보존 < 12", "do": "보존 생산 스킬을 못 부여 스킬보다 먼저", "gain": "+12% 피해", "confidence": "sim", "evidence": "run#42"}],
  "team_requirements": [{"need": "르누아르 소속 아군 ≥ 1", "impact": "-31% without", "evidence": "sens#7"}],
  "pitfalls": ["보존 부족 시 못 부여 자체가 실패"]
}
```
이 결과가 그대로 **팀 최적화의 Pair/Global 점수 입력**이 되고, **Agent 답변의 근거**가 된다.

## 5. 단계별 로드맵 (투자 대비 효과 순)

| 단계 | 내용 | 결과물 | 난이도 |
|---|---|---|---|
| A | Spec DSL 설계 + 인격 3~5개 수동/LLM 컴파일 + 테스트 | spec 품질 기준 | 중 |
| B | **정적 분석기** (자원 흐름, 브레이크포인트, 도달 턴) | 가이드의 50%+ | 하~중 |
| C | 공통 전투 엔진 + 허수아비 시나리오 단일 인격 시뮬 | 운용 순서 규칙 | 상 |
| D | 정책 탐색 + 결정 트리 규칙 추출 | 상태별 규칙 | 상 |
| E | 팀 시뮬 (소속·충전 공급 등 상호작용) + 민감도 | 팀 요구사항 정량화 | 상 |
| F | 전체 인격 배치 컴파일 + 신규 인격 증분 파이프라인 | 시즌 업데이트 대응 | 중 |

**추천: A→B를 최신 시즌 인격(르누아르 계열 #202~#204처럼 서로 엮인 묶음)으로 먼저 돌려 가치 검증 후 C로 진행.**

## 6. 열린 질문
- 공통 규칙(피해 공식, 합 세부, 공명 판정)의 정확한 출처: 공식 정보가 없으면 커뮤니티 검증 자료 + 사용자 실측으로 보정
- 대상 콘텐츠: 거울 던전(에고 기프트 개입) vs 굴절 철도/보스전 → 시나리오 우선순위 결정 필요
- 에고 기프트·E.G.O를 1차 범위에 넣을지
