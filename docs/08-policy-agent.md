# 08. 정책 에이전트 설계 (2026-10-28, 초안)

M2 정책은 "두 칸 중 높은 스킬" 고정 규칙이다. 목표는 **나중을 위해 지금 손해를 보는 선택**까지 하는 정책:
빌드업(스택 쌓고 터뜨리기), 카드 아끼기(S3 를 다음 턴 조건까지 보관), 아군 밀어주기(진동 깔아주기 등), 일부러 약한 스킬.

## 1. 원칙: 수치는 엔진, 판단 구조는 탐색, 말과 가설은 LLM

| 층 | 맡는 것 | 이유 |
|---|---|---|
| 엔진 (`engine/runtime`) | 결과 계산 (코인·피해·자원) | 이미 있음. LLM 은 확률·누적 효과 계산을 틀린다 |
| **탐색 정책** | 매 턴 선택 = 미래 가치로 비교 | "지금 약한 스킬"의 이득은 몇 턴 뒤에 나타남 → 시뮬해 봐야 보임 |
| **LLM 하네스** | 전략 가설 제안, 탐색 결과 해석, 규칙 추출·설명 | 결정 하나에 롤아웃 수천 번 → LLM 을 안쪽 루프에 넣을 수 없음 (비용·지연). 바깥 루프에서 씀 |

빌드업·밀어주기를 따로 규칙으로 만들 필요는 없다. **평가를 "몇 턴 뒤까지 팀 전체 결과"로 하면 저절로 나온다.**
보존을 쌓는 S2 가 이번 턴 피해는 낮아도 3턴 합계가 높으면 탐색이 고른다. 아군 피해가 목표에 들어가면 진동 깔아주기도 고른다.

## 2. 탐색 정책 (단계별)

1. **탐욕 기준선** — 이번 턴 기대 피해 최대. 비교 기준
2. **롤아웃 정책** (첫 구현) — 후보 행동마다 K 회 × H 턴을 기준 정책으로 굴려 평균 목표값 비교 → 최선 선택
   - 기준 정책을 개선하는 것이 보장되는 가장 단순한 방법. 빌드업을 H 턴 안에서 포착
   - 후보: 유닛당 (칸 0 / 칸 1 / 수비) × 대상
3. **팀 단위** (M3 이후) — 6명 결합 행동은 (3×대상)^6 → 한 명씩 나머지를 고정하고 개선 반복 (좌표 상승). 순서는 속도가 정하므로 선택만 고르면 됨
4. **ISMCTS** — 롤아웃으로 부족할 때. 2턴 이상 깊은 계획(S3 보관 후 연계 등)

### 정보 공정성 (중요)
덱 **순서**는 플레이어가 모른다 (구성만 앎: 남은 카드 = 6장 − 나온 카드). 롤아웃에서 실제 덱 순서를 그대로 쓰면
"다음에 S3 가 나올 걸 아는" 반칙 정책이 된다 → 롤아웃마다 **남은 덱을 다시 섞어서** 시작 (결정화, determinization).
코인 결과·속도 주사위도 미래 것은 새 난수.

### 목표 함수 (사용자 확인 2026-10-28)
**적 처치까지 걸리는 턴 수 + 생존**. 지평 H = 3~4턴 (빌드업은 보통 그 안에서 끝남).
- 처치 턴은 분수: 처치한 턴 t 에서 `t − 1 + (그 턴 시작 체력 / 그 턴 피해)`
- 지평 안에 못 잡으면 `H + 남은 체력 / 마지막 턴 피해` — 빌드업이 끝난 상태의 피해 속도로 나머지를 추정
- 생존: 아군 사망 1명 = +10턴, 체력 비율 손실 1.0 = +2턴 (`Objective` 가중치, 조정 가능)

LLM 하네스는 **오프라인 가이드 생성과 대화 조언 둘 다** 한다 (사용자 확인 2026-10-28).

## 3. LLM 하네스 (바깥 루프)

에이전트가 엔진을 **도구로** 쓴다. 숫자는 항상 도구 결과에서만 인용.

도구
- `state()` — 현재 상태 요약 (손패, 자원, 적 상태)
- `actions()` — 합법 선택지
- `evaluate(plan, horizon, runs)` — 계획(아래)을 시뮬레이션 → 목표값 분포
- `compare(a, b)` — 두 계획 차이와 유의성
- `trace(plan)` — 대표 진행 로그 (어느 턴에 무엇이 쌓였나)

**계획 = 조건부 규칙 목록** (작은 정책 DSL). 예:
```
when self.보존.potency < 3: prefer S2
when hand has S3 and self.아르뮈르 < 60: hold S3
when self.아르뮈르 >= 60: use DEF
else: highest
```
LLM 은 스킬 원문·LPDL 을 읽고 "이 인격은 보존 위력 3이 핵심이니 그때까지 S2 우선" 같은 가설을 계획으로 쓰고,
`evaluate` 로 검증하고, 결과를 보고 고친다 (생성 → 평가 → 수정 루프, lpdl compile 의 재시도 루프와 같은 구조).

쓰임새
- **운용 가이드 생성 (오프라인)**: 인격·팀마다 계획 후보를 만들고 탐색 정책과 비교 → 탐색 성능에 근접한 **사람이 읽을 수 있는 규칙** 채택
- **조언 모드 (대화)**: "이번 턴 뭐 써?" → 탐색 정책이 답하고 LLM 이 이유 설명 ("S1 이 이번 턴 −8 이지만 2턴 뒤 S3 가 +25")
- **노하우 수집**: 탐색이 탐욕과 다른 선택을 한 상태를 모아 LLM 이 공통점 요약 → `02` ⑥ 규칙 추출

백엔드: lpdlc-v2 compiler 와 같이 claude-code headless / api 선택.

## 4. 엔진 쪽 준비

- 정책 인터페이스: `policy(obs, legal) -> 팀 선택` — obs 는 덱 순서를 뺀 관측
- `run_turn` 에 결합 선택 주입 (지금은 유닛별 함수 호출) + 덱 재셔플한 복제 함수
- 속도: 롤아웃 1회 = H 턴 × 유닛 수. 현재 #202 1명 1턴 ≈ 2ms → 후보 3 × K 50 × H 4 ≈ 1.2s/결정. 팀·합이 들어오면 느려짐
  → 합은 열거 대신 몬테카를로 토스, 핫패스 최적화 필요

## 5. P1 구현 (2026-10-28)

- `engine/runtime/turn.py`: `run_turn` = `begin_turn` (턴 시작·속도, 선택 직전 상태) + `resolve_turn` (선택 반영 이후)
- `engine/runtime/policy.py`: `RolloutPolicy(rt, horizon=4, rollouts=32)` — `legal_choices`, `determinize`, 공통 난수, `Objective`
  - 후보: 칸 0/1 (같은 카드면 하나), 공격형 수비 스킬 (합 가능 반격 등) × 살아 있는 적
  - `.last` = 마지막 결정의 후보별 평균 목표값 (설명·노하우 수집용)
- `scripts/policy_eval.py <id> --hp 300 --games 100`: 정책별 처치 턴 분포·스킬 비율

결과 (#202 vs 허수아비 체력 300, 100판 같은 시드, H=4 K=32)

| 정책 | 평균 처치 턴 | 7턴 이내 | 스킬 비율 |
|---|---|---|---|
| top (위 칸) | 8.45 | 19% | S1 48 / S2 33 / S3 8 / 원킥 11 |
| highest | 8.14 | 23% | S1 42 / S2 38 / S3 9 / 원킥 11 |
| **rollout** | **7.64** | **47%** | S1 34 / S2 32 / S3 16 / 원킥 15 / DEF 2 |

롤아웃은 결정 1회 ≈ 0.7s (판당 5.5s). 팀·합이 들어오면 최적화 필요.

## 6. P2 구현 (2026-10-28)

`engine/agent/` — `python -m engine.agent <guide|eval|advise>`
- `plan.py`: 계획 DSL (JSON 규칙 목록, 조건식 = 제한된 파이썬 식). `PlanPolicy` 가 실행, `fired` 로 규칙별 발동 횟수 집계.
  이름·형식 오류는 `PlanError` 메시지로 LLM 에게 그대로 돌려줌
- `tools.py`: `evaluate` (처치 턴 분포, 스킬 비율 전체·턴별, 자원 trace, 규칙 발동), `spec_source` (인격 + 관련 키워드 LPDL),
  `battle_from_state` (조언 입력 JSON → 선택 직전 상태, 덱 = 6장 − 손패 − 셔플 후 사용 카드)
- `harness.py`:
  - `run_guide`: 분석 + 계획 N개 → 평가 → 결과 피드백 → 수정 (R 라운드) → 운용 가이드. 결과는 `data/agent/<id>/`
    (guide.md, best_plan.json, candidates.json, transcript.md)
  - `advise`: 롤아웃 정책 후보별 점수 + LLM 설명
- 백엔드: lpdlc-v2 `ClaudeCodeBackend` (claude -p, 로그인 사용 — 셸의 ANTHROPIC_API_KEY 는 빼고 실행) / `AnthropicBackend`

손으로 쓴 한 줄 계획 "아르뮈르 ≥ 60 이면 DEF, 아니면 highest" = 7.73턴 (300판) — 롤아웃 7.64 에 근접.

첫 가이드 실행 (#202, 체력 300, 3라운드 × 3계획, 300판): highest 8.22 / **LLM 최고 계획 7.94** / 롤아웃 7.64
- LLM 이 원 킥 사이클(아르뮈르 ≥ 60 → DEF)은 찾았지만, 보존 빌드업 규칙(위력 < 3 → S2·S1)을 앞에 붙여 한 줄 계획(7.73)보다 나빠짐
- 3라운드는 계획 하나의 카드 이름 오류("S3v1")로 전체가 버려짐 → 계획별 오류 격리로 수정

하네스 개선 (2026-10-28)
- 평가에 표준오차, 같은 시드끼리 짝지은 차이 (`paired`) — 공통 난수라 계획 간 차이의 se 가 개별 se 보다 작음
- 라운드마다 상위 2개 계획의 **규칙 빼 보기** (delta = 뺀 것 − 원래, 음수 = 해로운 규칙) 를 피드백
- 전체 라운드 순위표, 같은 계획 재평가 생략 (캐시), 기본 4라운드
- 최고 계획 선택: 1위와 짝지은 차이가 2 se 안이면 **규칙이 적은 쪽** (복잡한 규칙이 노이즈로 이기지 않게)

재실행 결과 (4라운드 × 3계획): **LLM 최고 계획 = "아르뮈르 ≥ 60 → DEF, 나머지 highest" 7.727 ± 0.042턴**
- 1라운드의 빌드업·S3 보관 규칙을 빼 보기로 해롭다고 확인 (빼면 −0.45 ~ −0.74턴) → 2라운드부터 제거
- 4라운드 1위(7.707, 규칙 2개)는 최고 계획과 차이 0.02 ± 0.018 → 노이즈로 판정, 규칙 1개짜리 채택
- 가이드에 "시도했지만 해로웠던 아이디어"와 근거 수치가 함께 남음

## 7. 다른 인격으로 검증: #204 (2026-10-28)

#204 브랜드 매니저 = 가호 100 을 쌓아 수비 스킬(묵시)을 S3 variant 1 로 바꾸는 빌드업 인격 (compiled spec).
엔진 보강: `prop inherit` (진동 → 진동 - 보존, 충전 → 보존), 수치형 키워드 부여(약속된 못), [부여 시] 수량 수정,
[전투 시작시] replace 유지, 공격하지 않는 수비 스킬 처리, #204 훅 4개 (`engine/runtime/hooks.py`, 나머지는 단독전 무관 NOOP).

결과 (평균 처치 턴, 300판)

| | hp 200 | hp 300 | hp 500 |
|---|---|---|---|
| highest | | 9.91 | |
| 롤아웃 (기준 정책 highest) | | 9.03 (60판) | |
| 롤아웃 (기준 정책 = 아래 계획) | | 8.95 (60판) | |
| LLM, hp 300 하나로 평가 → "가호 100 and turn >= 7 → DEF" | 6.89 | **8.54** | 12.13 |
| LLM, hp 200/300/500 평균으로 평가 → "가호 100 → DEF" | **6.13** | 8.65 | **11.71** |

발견
1. **롤아웃이 계획보다 못함**: 기준 정책(highest)이 DEF 를 안 쓰니 롤아웃이 가호 100 의 가치를 못 봄. 기준 정책을 계획으로 바꿔도
   8.95 — 지평 4턴 + "마지막 턴 피해로 외삽" 이 큰 한 방(S3v1) 직후 상태를 과대평가. 롤아웃은 값 추정 개선 전까지 상한 기준이 아님
2. **과적합**: 한 체력에서만 평가하면 LLM 이 `turn >= 7` 같은 체력 맞춤 규칙을 찾음 → 다른 체력에서 손해.
   하네스 기본값을 **여러 시나리오 평균** (`--hp 200,300,500`, `evaluate_set`) 으로 바꾸고 프롬프트에 "턴 수 대신 자원 조건" 명시 → 일반 규칙으로 수렴
3. LLM 이 `hand[1]` (칸 지정) 을 써서 형식 오류 — 조건식에 칸 지정이 필요하면 어휘 추가 검토

훅 확정 후 재평가 (사용자 확인 2026-10-28: [마지막 코인 시작 시] = 토스 직전 → `on coin_start ... coin.is_last` 로 LPDL 화,
원 킥 "가중치보다 낮은 대상 1당 +50%" = 대상 1명이면 +50%, 충전 소모 스킬 피해 보너스 = 첫 코인부터)

| 계획 | 평균 | hp 200 | hp 300 | hp 500 |
|---|---|---|---|---|
| highest | 10.34 | 7.06 | 9.68 | 14.27 |
| 가호 100 → DEF | **7.76** | **5.08** | 7.80 | **10.41** |
| 가호 100 and turn >= 7 → DEF | 8.64 | 6.77 | 7.66 | 11.48 |

단독전 보존 위력은 8턴에도 ≈2 — 못 부여가 턴당 1회 미만 (S1 은 못 없음, 심판! 은 르누아르 아군 공격 때만).
사용자: 팀이면 턴당 못 2회 → 소모 8 이상 → 4~5턴에 위력 3. → M3 팀 시뮬에서 재확인

## 8. 롤아웃 개선 (2026-10-28)

속도: 이벤트별 블록 색인 (스킬·코인·패시브·키워드가 그 이벤트 블록을 가질 때만 실행, 보유 키워드만 훑음),
`Frame.child` 를 얕은 복사로 → 결정 1회 ≈ 0.3s (#204, H=4 K=32, 이전 대비 2~3배). 결과는 동일.

값 추정: `RolloutPolicy(horizon=None)` = 처치까지 끝까지 굴림 (max_turns 30). `base=` 에 계획 정책 사용 가능.

#204, hp 300, 60판 (같은 시드), 평균 처치 턴

| 정책 | 턴 |
|---|---|
| 계획 "가호 100 → DEF" (LLM) | 7.75 |
| 롤아웃 H=4, 기준 highest | 7.98 |
| 롤아웃 끝까지, 기준 highest | 7.82 |
| 롤아웃 H=4, 기준 = 계획 | 7.90 |
| **롤아웃 끝까지, 기준 = 계획** | **7.25** |

- 지평 4턴 + 외삽, 또는 DEF 를 안 쓰는 기준 정책 중 하나라도 있으면 계획을 못 넘음
- 둘 다 고치면 계획보다 0.5턴 빠름 = **LLM 계획 위에서 탐색이 한 단계 더 개선** (정책 반복)
- → 다음: 이 롤아웃이 계획과 다르게 고른 상태를 모아 LLM 에게 피드백 (계획 개선 루프)

## 9. 계획 개선 루프 (2026-10-28)

`python -m engine.agent refine <id> <plan.json>` — 계획을 기준 정책으로 한 롤아웃(끝까지)으로 판을 진행하며
계획과 다르게 고른 장면(상태·덱 구성·이득)을 모음 (`distill.py`) → LLM 이 패턴을 규칙화 → 여러 체력 평가 + 빼 보기 → 반복.
조건식에 `deck`, `hand[0]/hand[1]`, `count/len/min/max` 추가.

#204 결과 (시작 "가호 100 → DEF" 7.76 = 5.08 / 7.80 / 10.41)

## 10. M3 팀 vs 보스 (2026-10-28)

확정 (사용자): 단일 보스, 적 대상 = 살아 있는 아군 균등 랜덤 + 선택 전 공개, 합 = **가로채기 포함**
(아군이 적 주사위 E 를 대상으로 하고 속도 ≥ E → E 가 누구를 노렸든 그 아군과 합, 여럿이면 마지막으로 고른 아군), 팀 = 르누아르 3인.

구현
- `state`: `Unit.dice/speeds/pattern`, `Battle.intents/pattern_pos`. `turn.begin_turn` 이 적 주사위 속도·의도(패턴 순환, 랜덤 대상) 공개
- `turn.resolve_turn`: 합 짝짓기([전투 시작시] 교체 뒤) → 속도순 실행, 합은 `run_clash`, 사망·흐트러짐 시 취소
- 수비 반응: 방어·반격은 자기 속도에 행동하지 않고 **이번 턴 자신에게 처음 들어오는 공격**에 반응 (방어 = 위력만큼 보호막 후 피격,
  반격 = 피해 뒤 일방 공격). **회피** = 이번 턴 나를 때리는 적의 모든 스킬에 코인마다 회피 위력 비교, 이기면 그 코인 회피
  (+ 흐트러짐 게이지 회복), 한 번이라도 맞으면 그 뒤로 계속 맞음 (사용자 확인 2026-10-28). 합 가능 반격은 공격 스킬로 취급
- 흐트러짐 피해(진동 폭발 등) = 다음 흐트러짐 선을 그만큼 앞당김 (`stagger_gauge`, 선이 깨지면 0) (사용자 확인). 판정은 직접 피해 때
- 심판!: #202 가 합에서 지면 [공격 시작 전]이 없어 발동 안 함 (사용자 확인)
